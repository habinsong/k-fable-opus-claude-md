## 2. 이 모델의 네이티브 작업 운용
모델 전체 특성은 상위 폴더의 [`README.md`](../README.md)가 안내하는 개요·운용·비판 문서를 따른다. 요약: 밀집 27B, SWE-bench Verified 최대 77.2(벤더 수치 인용), 로컬 코딩·도구 호출 후기가 비교적 풍부, PR 검토가 병목이라는 후기, C/C++·Rust 독립 평가 없음.

**개발 보조로 쓸 때**
- **소규모 유지보수 작업에 쓸 만하다는 후기가 있다.** 한 후기는 이 모델이 ggml-org 유지보수 작업에 쓸 만하다고 전하면서 PR 검토가 병목이라고 했다. 개인 경험이다. 모델이 만든 변경은 사람이 PR 수준으로 검토하고, 검토 부담이 생산성을 깎을 수 있음을 계획에 넣는다. [부분: 개인 후기]
- **C++·Rust·시스템 코드의 언어별 독립 평가는 찾지 못했다.** [미확인] 메모리 관리, 동시성, 수명, ABI는 문법이 맞아도 틀리기 쉬우므로 핵심 변경에는 쓰지 않고, 쓴다면 sanitizer(ASan·UBSan·TSan)와 테스트를 지시문으로 강제한다. 핵심 변경은 `claude/sonnet-5.5` 이상, `gpt-6.1-sol`, `gemini-4-argon` 문서를 따르거나 우리 코드로 같은 과제를 비교한다.
- **SWE-bench Verified 77.2는 벤더 수치를 옮긴 서술이다.** 하네스와 조건을 확인하지 못했고 독립 재현이 없다. 35B-A3B의 73.4와의 차이도 같은 한계 안에서 읽는다. [부분: 벤더 주장]
- **35B-A3B보다 27B를 선호한다는 후기가 있다.** 한 후기는 35B-A3B가 3배 빠르지만 27B를 선호한다고 했고, 다른 후기는 A3B Q4가 같은 작업을 도는 동안 같은 자리를 돌다가(루프) 더 오래 걸렸다고 했다. 코딩 에이전트 용도에서는 속도보다 완결성이 중요할 수 있다. 개인 후기이며 양자화 수준(Q4 대 Q6)이 달라 직접 비교가 아니다. [부분: 개인 후기]
- **Gemma 4와의 비교는 갈린다.** 에이전트·도구 호출에서는 이 계열이 낫다는 후기가 많았고, 일부 코드 생성 과제에서는 Gemma 4 31B가 낫다는 후기도 있다. 같은 기기·양자화·과제·샘플링으로 `gemma-4-31b`와 직접 비교한다. [부분: 개인 후기]
- **로컬 실행의 이점은 소스가 외부로 나가지 않는 것이다.** 이 이점은 정확도를 보증하지 않는다. 한 보고에서 9070 XT 기준 초당 약 13~15 토큰이라 빌드-테스트 루프의 지연이 크다. 한 번에 크게 묻고 한 번에 검증한다. [부분: 개인 후기]
- **도구 호출 파서와 템플릿을 런타임 버전에서 확인한다.** 서빙 예시는 `qwen3` 추론 파서와 `qwen3_coder` 도구 호출 파서를 쓰고 llama.cpp는 `--jinja`로 네이티브 도구 호출을 쓴다. Unsloth 페이지가 도구 호출의 중첩 객체 파싱 개선을 언급한다. 열린 버그의 현재 상태는 확인하지 못했다. [부분]
- **에이전트 루프에 안전장치를 먼저 둔다.** 파괴적 명령 차단(권한·훅), 작업 디렉터리 격리, 시간·토큰 한도를 설정하고, 완료 보고는 빌드·테스트·sanitizer 출력과 `git diff`로 확인한다. 테스트·경고·sanitizer 설정이 바뀌었는지도 확인한다. 억제 지시문을 넣거나 검사를 끄는 제안은 따르지 않는다.

**애플리케이션에 내장할 때**
- 로컬 런타임(llama.cpp 등)을 링크하면 런타임과 가중치 라이선스를 각각 확인한다. 가중치는 여러 목록에 Apache 2.0이라고 적혀 있으나 LICENSE 원문으로 확인한다(§1.5). 모델 호출은 별도 프로세스와 최소 권한으로 격리하고, 모델이 만든 경로·명령·코드를 그대로 실행하지 않는다. 파서·역직렬화 코드는 퍼징 대상으로 본다(§3.1). 시스템 경로, 레지스트리, 드라이버, 부트 설정, 서명 키는 승인 없이 건드리지 않는다. [부분]
